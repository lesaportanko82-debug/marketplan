====================================
1. РЕЖИМ РАБОТЫ
====================================
Ты не должен останавливаться после первых найденных проблем.
Ты не должен ограничиваться одной секцией.
Ты не должен делать выборочную проверку.
Ты не должен проверять только “основные” экраны.
Ты обязан пройти приложение полностью и системно.

Работай только так:
1. Сначала составь карту приложения по всем найденным экранам, страницам, разделам, секциям, состояниям и ключевым сценариям.
2. Затем построй audit matrix, чтобы ничего не пропустить.
3. Затем проходи приложение последовательно, экран за экраном, блок за блоком, действие за действием.
4. Каждую найденную проблему не просто фиксируй в отчете, а сразу исправляй.
5. После каждого блока исправлений делай regression check, чтобы починка не сломала соседние части.
6. В конце сделай финальный повторный regression pass по всему приложению.

Нельзя:
- делать поверхностный осмотр;
- ограничиваться одним сценарием;
- пропускать мелкие элементы;
- оставлять сломанные элементы без решения;
- заменять реальную проверку общими словами;
- писать “похоже все работает”, если все реально не проверено;
- останавливаться на первом уровне интерфейса.

3. ПРИНЦИП ПРОВЕРКИ
====================================
Работай по принципу exhaustive sequential audit.

Для каждого экрана и блока проверяй:

1. Rendering
- отображается ли корректно
- не ломается ли layout
- нет ли пропавших блоков
- нет ли наложений
- нет ли пустых дыр

2. Interaction
- все ли кликается
- есть ли реакция
- происходит ли нужное действие
- нет ли мертвых элементов

3. State transitions
- что происходит до действия
- что происходит во время
- что происходит после
- правильно ли меняются статусы
- не ломается ли соседний UI

4. Data correctness
- правильные ли данные отображаются
- правильные ли данные сохраняются
- совпадает ли summary с реальными данными
- правильно ли работают фильтры/поиск/сортировка

5. Business correctness
- правильна ли логика расчета
- нет ли неверных формул
- нет ли логических дыр
- не противоречат ли блоки друг другу

6. UX correctness
- понятен ли flow
- не слишком ли много шагов
- нет ли тупиков
- нет ли confusing states
- понятно ли, что делать дальше

====================================
4. ПРАВИЛА ПО ФИКСАМ
====================================
Каждый найденный баг нужно:
1. классифицировать;
2. объяснить кратко и точно;
3. сразу исправить;
4. проверить после исправления;
5. проверить соседние зависимости;
6. пометить как fixed только после повторной проверки.

Классифицируй баги минимум по типам:
- functional bug
- logic bug
- calculation bug
- data bug
- validation bug
- UI inconsistency
- UX bug
- navigation bug
- state bug
- access bug
- performance smell
- copy/content inconsistency

Приоритеты:
- critical
- high
- medium
- low

Не оставляй баг “на потом”, если его можно исправить сейчас.
Оставлять можно только то, что действительно блокируется архитектурным ограничением — и это надо прямо указать.

====================================
5. ПРАВИЛА ПРОТИВ ПРОПУСКОВ
====================================
Чтобы не пропустить ничего, ты обязан:

- сначала составить полный inventory экранов;
- затем inventory всех интерактивных элементов по экранам;
- затем inventory всех пользовательских сценариев;
- затем inventory всех расчетных и зависимых блоков;
- затем пройти их по очереди;
- помечать покрытие проверки явно;
- не переходить к финалу, пока coverage table не заполнена.

Если элемент найден, но не проверен — он считается не пройденным.
Если сценарий есть, но не протестирован end-to-end — он считается не пройденным.
Если блок связан с расчетом, но формула не проверена — он считается не пройденным.
Если экран визуально открыт, но не проверены его состояния — он считается не пройденным.

6. ОСОБО ЖЕСТКАЯ ПРОВЕРКА ДЛЯ МОЕГО ПРИЛОЖЕНИЯ
====================================
Так как это маркетинговый планер, проведи особенно жесткий аудит для:

- логики создания проекта;
- редактирования проекта;
- переключения между проектами;
- сохранения данных по проектам;
- метрик и их формул;
- budget planners;
- campaign planners;
- контент-планов;
- брендинговых блоков;
- сегментации ЦА;
- аватаров аудитории;
- summary dashboards;
- таблиц и фильтров;
- экспорта и отчетов, если они есть;
- связей между страницами одного и того же проекта;
- сохранения черновиков и опубликованных состояний, если есть;
- повторного открытия уже созданных сущностей;
- корректности отображения после reload / revisit.

Проверь, нет ли:
- сломанных формул;
- рассинхрона между секциями;
- “визуально есть, но реально не работает”;
- данных, которые вводятся, но не влияют на зависимые блоки;
- счетчиков, которые показывают фиктивные или неактуальные данные;
- полей, которые теряются после сохранения;
- конфликтов между ручным вводом и автоподсчетом;
- скрытых ошибок при редактировании существующей сущности.

====================================
7. ПОВЕДЕНИЕ ПРИ НАХОЖДЕНИИ ПРОБЛЕМ
====================================
Не останавливайся после нахождения ошибки.
Не выдавай просто список багов.
Не спрашивай, нужно ли чинить.
Сразу исправляй.

Режим работы:
- нашел баг;
- определил причину;
- внес исправление;
- перепроверил;
- сделал локальный regression;
- пошел дальше.

====================================
8. ЕСЛИ НАХОДИШЬ НЕЯСНОСТЬ
====================================
Если логика элемента неочевидна:
- не игнорируй его;
- не пропускай;
- выбери наиболее логичную MVP-интерпретацию;
- реализуй ее последовательно;
- кратко зафиксируй это как assumption.

Но не уходи в редизайн продукта.
Не перепридумывай приложение.
Сохраняй существующую логику максимально бережно.

====================================
9. ФОРМАТ РЕЗУЛЬТАТА
====================================
Работай строго в таком формате:

Шаг 1. App inventory
- полный список найденных экранов
- список секций по экранам
- список интерактивных элементов
- список сущностей
- список сценариев

Шаг 2. Audit matrix
Таблица покрытия вида:
- Screen / Section
- Element / Flow
- What is being tested
- Status: not checked / in progress / fixed / deferred
- Notes

Шаг 3. Sequential audit + fixes
Для каждого экрана:
- что проверяется
- что найдено
- что исправлено
- какие зависимости перепроверены
- итоговый статус

Шаг 4. Regression pass
- повторная проверка уже исправленных участков
- проверка, что новые правки не сломали соседние части

Шаг 5. Final coverage report
- что проверено
- что исправлено
- что отложено осознанно
- какие риски остались
- какие места были самыми уязвимыми

====================================
10. КРИТИЧЕСКИЕ ЗАПРЕТЫ
====================================
Не делай:
- выборочную проверку;
- общие советы вместо реального аудита;
- поверхностное “вроде работает”;
- остановку после первого прохода;
- пропуск мелких элементов;
- пропуск hidden states;
- пропуск формул и зависимых расчетов;
- фиктивные фиксы без перепроверки;
- редизайн вместо отладки;
- замену логики временными заглушками без пометки.

====================================
11. ФИНАЛЬНАЯ ЦЕЛЬ
====================================
Ты должен провести максимально полный, последовательный и жесткий аудит приложения, найти и исправить максимум багов сразу, не пропуская экраны, элементы, состояния, сценарии, формулы, переходы и связи между секциями.

Итогом должен стать не отчет “что сломано”, а реально более стабильное, логичное и рабочее приложение, прошедшее полный последовательный аудит с немедленным исправлением найденных проблем.
